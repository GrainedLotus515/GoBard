# NF HOPE album failure investigation — 2026-10-15

The user stopped the old VPS instance themselves. Investigation concerns only
local `gobard-v2-test`, running the v2 feedback code from `6faf849`, image
`sha256:6f5bb7484e1b6d7135db84e03bd07bfeb6002b0f07a3e6d30efa2bd57552d711`.
The container remained online during these probes; no production cache or VPS
was accessed. The user identified the failing playlist as NF's *HOPE* album.

`https://www.youtube.com/playlist?list=OLAK5uy_milshKgR-N66M5IZsSfZWQ74AyrScobNg`.

(`zpp6ZvJ351Q`). This matches the [official album order](https://shop.nfrealmusic.com/collections/music/products/hope-digital-download).

mapping those two failures to these names assumes unchanged album queue order.

These are successful recovery records, not proof of uninterrupted listening.

Two credential-free, isolated acquisition probes used the same runtime image,
canonical album video IDs and `extractionArgs` settings (all retries zero,
15-second socket timeout, `bestaudio[ext=webm]/bestaudio`, stdout acquisition).
No cache was mounted. Each subprocess had a 40-second deadline, an 8 MiB file
limit and a 32 MiB tmpfs; the container had 256 MiB RAM, 0.5 CPU and 64 PIDs.
Metadata was capped at 13 entries. Stderr inspection retained 16 KiB and exposed
only known diagnostic phrases, exit status and a fingerprint.

A separate paced MOTTO probe fed yt-dlp's pipe into FFmpeg with `-re`, pipe-only
input, stereo 48 kHz libopus encoding, 20 ms frames and null output. It used the
same image, 256 MiB/0.5 CPU/64 PID limits, 16 MiB tmpfs, 64 KiB per diagnostic
file and a 270-second deadline. The extractor exited 1 after a connection reset
(fingerprint `71f52cf8f8ad29f0`); FFmpeg exited 0 after encoding 166.8605 seconds.
Total elapsed time was 168,351 ms, below the timeout. Thus clean codec EOF again
did not mean a complete source. This reproduces a mid-stream acquisition
failure independently of Discord; it is not a real voice-delivery test or the
Go pipeline itself. It does not reproduce the two startup failures.

Fast download success versus paced-stream failure is evidence to investigate
network backpressure and acquisition strategy. It does not identify which
network endpoint reset the connection or establish a CPU or CAPTCHA cause.

## Changes and remaining work

The diagnostic patch carries an optional public track ID from validated
metadata through session/retry to the authoritative terminal event. It also
recognizes HTTP 403 and unavailable requested-format diagnostics, with specific
safe Discord guidance. These are possible diagnostic classes, **not claims
about the two original unknown failures**. Unknown stderr was intentionally
not persisted, so those historical reasons cannot be recovered from hashes.

Retry budgets and extraction behavior are unchanged. No cookies, account
credentials, alternative clients, provider fallbacks or auth bypasses were
introduced. The repeated streaming resets and intermittent zero-frame failures
remain unresolved. Reworking acquisition to decouple network reads from voice
pacing needs explicit byte/disk budgets, cancellation tests and startup-latency
measurements before claiming a reliability improvement.

Validation and local image availability are recorded in [status](status.md).
The strict SDK lifecycle release blocker also remains unchanged.
